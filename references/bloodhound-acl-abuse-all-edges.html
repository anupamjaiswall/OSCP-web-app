🧭 You landed a TGT / reset a password — now what?

  
Every chain on this page ends the same way: you now effectively are the target principal (or you reset their password — same outcome). That's a means, not the goal. The actual next step is always the same two questions, answered by that principal's own info panel in BloodHound — the same right-hand panel you were just reading values out of, scrolled down past "Object Information" to its collapsible tabs:

  
    
    
  • Sessions — where they're logged in right now. A session on a box = an immediate lateral-movement target (dump LSASS there, grab whatever's cached).
    • 
    
  • Member Of — groups they belong to. Landed in Domain Admins / Backup Operators / Account Operators / anything with DCSync? You're done, skip straight to looting.
    • 
    
  • Local Admin Privileges — machines you can now psexec/wmiexec/evil-winrm into directly as this principal.
    • 
    
  • Execution Privileges — same idea, for WinRM/PSRemote-style access specifically.
    • 
    
  • Outbound Object Control — new ACL edges starting FROM this principal. If this is > 0, you're not finished: treat this principal as the new "Controlled user" in the panel up top, and work the chain again from the top of this page.
    • 
    
  • Inbound Object Control — who else can control this principal (useful context, rarely your next move).
    • 
  

  
These tabs only know what the last SharpHound/bloodhound-ce-python collection saw — if you suspect something changed (you just added yourself to a group, say), re-run collection before trusting them. In a hurry, a quick-and-dirty cross-check from the CLI: nxc smb <dc-ip> -u '<principal>' -H <hash> --shares (what can they touch over SMB) and nxc winrm <dc-ip> -u '<principal>' -H <hash> (can they WinRM anywhere) — both work with a hash, no ticket needed.

⚠️ Timing — this isn't instant

    
The task only fires on the next Group Policy refresh on each affected computer — and that interval is not the same on a DC as everywhere else: regular member computers refresh every ~90 min (plus a random 0–30 min offset), but domain controllers refresh computer policy every 5 minutes by default, no offset (Microsoft Learn). "Default Domain Policy" applies to the DC too, so for this exact chain, 5 minutes is the number that matters — if it's been less than that since you pushed the task, it just hasn't fired yet. If you already have any shell on a box this GPO applies to (including the one you're about to get), gpupdate /force there pulls it immediately instead of waiting either interval. Option B needs your listener running before you push the task — you don't get to pick the exact moment it calls back; Option A has no such window, which is why it's the default recommendation and doubles as a free timing check: if the new Domain Admin account shows up but your shell still doesn't call back, the GPO/task mechanism is confirmed working and the problem is specific to the shell payload (AMSI/Defender flagging that exact well-known PowerShell one-liner, or egress filtering — not a GPO issue). Both options fire on every computer the GPO applies to by default — add -filter-enabled -target-dns-name <dc-fqdn> to either command if you want to restrict it to one host, e.g. get the DC's FQDN from the banner in nxc smb <dc-ip>.

Same panel up top, same outcomes as the Kali tab — just driven from a Windows shell: PowerView for ACL/property writes, Rubeus for anything Kerberos, Mimikatz for LSASS-level abuse (DCSync, pass-the-hash), PowerMad/Whisker/SharpGPOAbuse for the rest, native AD cmdlets/dsacls as the no-extra-tooling fallback.




  
⚠️ Hash vs. plaintext works differently here than on Kali

  
Rubeus and Mimikatz take a raw NTLM hash directly (/rc4:, /ntlm:) — exactly like bloodyAD/impacket on the Kali tab, nothing changes for those. PowerView cannot — anything built on -Credential needs either a real plaintext password (to construct a PSCredential) or, far more commonly on the exam, you're simply already running as the controlled user (you got a shell as them) and pass no -Credential at all, letting Windows' own Kerberos/NTLM context handle auth. If all you have is a bare hash and no session as that user yet, pass-the-hash it into a fresh process first — Mimikatz sekurlsa::pth below — then run the PowerView commands from inside that spawned shell with -Credential dropped entirely. Every PowerView command on this tab shows the plaintext-PSCredential form; if your panel only has a hash, mentally replace it with "already running as this user" instead.

ACE write succeeds but the right "doesn't work" a bit lateradminCount=1 on the target — AdminSDHolder/SDProp resets protected objects' ACLs roughly every 60 min, wiping anything you addedAct immediately after writing; if you need persistence instead, target a computer edge (RBCD/Shadow Creds), which doesn't rely on a surviving ACE

  
Every Kerberos step (Shadow Creds, RBCD ticket, DCSync via -k) errors outClock skew >5 min from the DCsudo ntpdate <dc-ip> before anything else

  
Name or service not known on the realm (e.g. DOMAIN.LOCAL:88)Kerberos needs to resolve the domain name itself to find the KDC, and nothing local knows it-dc-ip fixes this one case directly — or the Step 0 /etc/hosts line near the top, which fixes it permanently

  
Same error, but on the target hostname (e.g. fileserver01.contoso.local:445) — and -dc-ip is already set and doesn't help-dc-ip only feeds the Kerberos/KDC code path. It does nothing for the separate connection a tool like psexec opens to the actual target — that still needs real DNS or /etc/hostsThe Step 0 /etc/hosts line covers both at once; -dc-ip alone never will

  
secretsdump specifically: Name or service not known where the "hostname" in the error is actually your whole domain/user:pass string, slashes and allsecretsdump's target format is domain/user:pass@HOST — the @host is required, not decoration. Leave it off and impacket can't split out a domain/user/password at all, so it tries to resolve the entire leftover string as one literal hostnameAdd @<dc-ip> to the identity string (or -target-ip <dc-ip>, same effect) — this is what the DCSync section's step 2 now does by default

  
[-] CCache file is not found. Skipping...Benign. KRB5CCNAME was set (or left over from an earlier step) to a filename that doesn't exist yet, so the tool says so and requests a fresh ticket anyway — this is noise before the real attempt, not the error itselfIgnore it, or unset KRB5CCNAME first if it's distracting. Read the line(s) that follow for the actual result

  
No such file or directory: 'Administrator.ccache' right after a successful getSTgetST does not save to a simple <user>.ccache — it names the file after the impersonated user, the SPN and the realm (e.g. Administrator@cifs_HOST.DOMAIN@DOMAIN.ccache), which most guides quietly assume awayEvery getST chain on this page now does export KRB5CCNAME=$(ls -t *.ccache | head -1) instead of guessing the name — grabs whatever file was just written, however it's spelled

  
impacket-addcomputer fails / access deniedMachineAccountQuota = 0, or you've already added 10 (default cap) this wayUse the Shadow Credentials chain instead — it needs no new computer account

  
gettgtpkinit fails with KDC_ERR_PADATA_TYPE_NOSUPPNot a syntax error — the DC has no certificate configured for PKINIT (no AD CS in this domain). A Kerberos TGT from this cert is impossible here, full stopUse the same cert a different way: Pass-the-Cert over LDAPS/Schannel instead of Kerberos — see the fallback box right under Shadow Creds in the User/Computer sections above

  
dacledit / bloodyAD write rejected over plain LDAPDC enforces LDAP signing/channel binding for writesAdd -use-ldaps (dacledit) or point bloodyAD at ldaps://

  
bloodyAD set object / add uac / remove uac errors or looks unrecognizedThese are less common bloodyAD subcommands than set password — more likely to have drifted between versionsRun bloodyAD --host <dc> -d <domain> -u <you> -p <pass> set object --help (or add uac --help) fresh before trusting the generated line blind
